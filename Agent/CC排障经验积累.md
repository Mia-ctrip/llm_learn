Claude Code 排障经验沉淀

  一、模型配置体系与优先级

  Claude Code 的模型配置不是单一的，而是分层的：

  | 配置层级                     | 控制范围                       | 优先级    | 设置方式            |
  |--------------------------|----------------------------|--------|-----------------|
  | /model 命令                | 主对话、Compact                | ⭐⭐⭐ 最高 | 会话级，临时生效        |
  | ANTHROPIC_MODEL 环境变量     | 主模型（无 /model 时）            | ⭐⭐ 中   | 全局/用户级          |
  | ANTHROPIC_DEFAULT_* 环境变量 | 后台任务（Token 计数、标题、摘要、前缀提取等） | ⭐ 低    | 全局/用户级          |
  | 内置默认值                    | 所有上层未定义时                   | 最低     | Claude Code 代码内 |

  关键认知： 在 Claude 中修改 /model 只影响主对话，后台任务默认使用环境变量或内置默认值。如果网关模型更新，需要同时更新环境变量配置，单纯改 /model 不够。

  ---
  二、排障工具与方法

  2.1 Debug 日志的价值

  claude --debug

  - 输出完整的 API 调用栈和错误信息
  - 能看到并发调用（Promise.all）和重试行为
  - 帮助快速定位是哪个功能失败、用的是什么模型
  - 日志存储在 ~/.claude/debug/ 中，可供事后分析

  实战意义： 本次排障中，debug 日志清晰地显示了多个模型返回 400/500，以及它们的调用栈，直接指向了"后台任务模型不支持"这个问题。

  2.2 /context 命令的诊断价值

  - 能准确反映当前会话的上下文占用分布
  - 如果 /context 本身失败（比如返回 400），说明模型配置有问题
  - 帮助区分"是否真的占满"vs"用量上报错误"

  实战意义： 通过 /context 的失败→修复→成功这个过程，确认了问题的根本原因。

  ---
  三、Claude Code 的架构特性

  3.1 后台任务的独立模型调用

  Claude Code 不是单一模型调用，而是多个并发的、用不同模型的请求：

  主对话请求 → ANTHROPIC_MODEL（或 /model 设置）
    ├─ Compact → 同上
    ├─ /context Token 计数 → ANTHROPIC_DEFAULT_SONNET_MODEL（thinking 开启时）
    ├─ Bash 前缀提取 → ANTHROPIC_DEFAULT_HAIKU_MODEL
    ├─ 会话标题生成 → ANTHROPIC_DEFAULT_HAIKU_MODEL
    └─ WebFetch 摘要 → ANTHROPIC_DEFAULT_HAIKU_MODEL

  关键发现： 网关返回 500 时，SDK 会对主请求进行指数退避重试。如果后台任务的某个调用返回 500，它可能阻塞或延迟主流程，导致 send 后长时间无响应。

  3.2 Shell 环境的隐性成本

  - 每次 Bash 调用，Shell 启动脚本（如 /etc/bash.bashrc）会执行
  - 脚本的输出（如欢迎横幅）会被写入工具返回结果中
  - 这些都会累积进上下文，加快占用速度
  - 特别在批量工具调用时，这个成本成倍增长

  实战启发： 在 Claude Code 环境中应该条件化输出，避免非交互式场景下的冗余信息。

  ---
  四、排障思路的启发

  4.1 从表现反推架构

  现象：
  - send 后卡顿但 API 返回错误
  - 上下文显示 0% 但实际应该有空间
  - /context 无法执行

  反推：
  - 有重试机制在阻塞主流程
  - 有多个独立的后台调用在使用不同的模型
  - 后台调用的失败会影响上下文占用的计算

  教训： 当工具出现多个症状时，不要只看单个症状，而要推敲背后的架构关系。

  4.2 分层修复的重要性

  修复顺序很关键：
  1. 先修环境变量（模型支持问题）→ 消除 400/500 错误
  2. 再用 /context 验证 → 确认占用是否真实
  3. 最后优化横幅输出 → 降低上下文增长速度

  如果顺序反了或跳步，会很难确认问题的真正原因。

  ---
  五、可复用的检查清单

  遇到类似问题时：

  - 运行 claude --debug 检查完整调用栈
  - 检查 ANTHROPIC_* 相关的环境变量配置
  - 运行 /context 或 /status 诊断当前会话状态
  - 确认网关的当前支持模型列表（通常在网关管理后台）
  - 检查用户的 Shell 配置是否在非交互环境下有冗余输出
  - 确认 Claude Code 版本是否过老（导致内置默认值过时）

  ---
  六、对后续维护的建议

  1. 模型版本管理： 当网关下架旧模型时，及时通知用户更新 ~/.bashrc 中的 ANTHROPIC_DEFAULT_* 变量
  2. 自动诊断： Claude Code 可以在启动时检查环境变量指向的模型是否被网关支持，提前告警
  3. 版本策略： 鼓励用户及时更新 Claude Code（自动包含新的默认模型），但也要处理好全局/用户级配置的优先级关系

# 第 0 章：GPU 通讯全景与度量方法

> 本章是整个系列的地图。先建立三个框架：**分层**（数据走多远）、**数量级**（每层多快）、**度量口径**（怎么算、怎么比）。后续每一章都是在某一层上展开。

---

## 0.1 为什么 AI Infra 工程师必须懂通讯

GPU 算力的增长远快于互联带宽。以 H100 SXM 为例，用"每搬运 1 字节需要配多少 FLOP 才能把 Tensor Core 喂饱"来衡量各层的相对代价：

| 数据来源 | 带宽（单向） | BF16 稠密 989 TFLOPS 下，每字节需配的计算量 |
|---------|-------------|------------------------------------------|
| HBM3（卡内） | 3.35 TB/s | ≈ 295 FLOP/B |
| NVLink4（卡间） | 450 GB/s | ≈ 2,200 FLOP/B |
| 400G NIC（跨机） | 50 GB/s | ≈ 20,000 FLOP/B |

数据每往外走一层，就需要多一个数量级的计算来掩盖它。分布式训练和推理的大部分工程问题，本质都是"让数据少走远路，走远路时别让计算干等"。

平台上常见的这几类工单，根因基本都在通讯：

- 单机 8 卡训练正常，扩到 2 机 16 卡吞吐没翻倍，甚至下降
- 训练跑了几小时突然卡住，最后报 NCCL timeout
- vLLM 开 TP=8 比 TP=4 还慢
- 同型号的两台机器，一台的 nccl-tests 结果只有另一台的一半

## 0.2 分层模型：按"数据走多远"划分

### 0.2.1 硬件分层

```
┌──────────────────────────────── 节点 A ─────────────────────────────────┐
│                                                                         │
│   CPU0 ── DRAM  ◄═══ UPI / xGMI ═══►  CPU1 ── DRAM                      │
│     │                                   │                               │
│   PCIe Switch ─── NIC0                PCIe Switch ─── NIC4    ◄── L1    │
│     │                                   │                               │
│  ┌──┴────────────┐                   ┌──┴────────────┐                  │
│  │ GPU0          │                   │ GPU4          │                  │
│  │ SM ⇄ L2 ⇄ HBM │ ◄── L0            │ SM ⇄ L2 ⇄ HBM │                  │
│  └──┬────────────┘                   └──┬────────────┘                  │
│     ╚═══════════════ NVSwitch ══════════╝                   ◄── L2      │
│                                                                         │
└───────────────────────────────────┬─────────────────────────────────────┘
                                    │  NIC ⇄ IB / RoCE 交换机 ⇄ NIC   ◄── L3
                              ┌─────┴─────┐
                              │  节点 B    │
                              └───────────┘
```

| 层级 | 范围 | 物理链路 | 软件接口 | 带宽量级（单向） | 延迟量级 | 章节 |
|------|------|---------|---------|-----------------|---------|------|
| **L0 卡内** | SM ↔ 寄存器/SMEM/L1 ↔ L2 ↔ HBM | 片上 crossbar、HBM 总线 | CUDA kernel 的 load/store、shuffle、TMA | HBM 2~8 TB/s，L2/SMEM 更高 | 几十 ns ~ 几百 ns | 第 1 章 |
| **L1 主机↔卡** | CPU 内存 ↔ GPU 显存 | PCIe Gen4/5；Grace 平台为 NVLink-C2C | `cudaMemcpy`、pinned memory、UVM | PCIe Gen4 x16 ≈ 25 GB/s 实测，Gen5 ≈ 50 GB/s 实测；C2C 450 GB/s | 微秒级 | 第 2 章 |
| **L2 节点内卡间** | GPU ↔ GPU（同一台机器） | PCIe P2P、NVLink Bridge、NVSwitch | `cudaMemcpyPeer`、CUDA IPC、NCCL P2P/SHM | PCIe P2P 20~50 GB/s；NVLink 300~900 GB/s | 微秒级 | 第 3 章 |
| **L3 跨节点** | GPU ↔ 另一台机器的 GPU | NIC + IB/RoCE 交换网络 | RDMA Verbs、GPUDirect RDMA、NCCL NET | 每 NIC 25~100 GB/s（200G~800G） | 几微秒 ~ 十几微秒 | 第 4 章 |
| **L3+ 机柜级** | 多个 compute tray 组成一个 NVLink 域 | NVLink Switch Tray（如 GB200 NVL72） | 对软件表现为"节点内" NVLink | 每 GPU 900 GB/s | 微秒级 | 第 3、4 章 |

常见 GPU 的单卡 NVLink 总带宽（单向）：

| GPU | NVLink 代际 | 链路数 | 单向总带宽 | 官方宣传值（双向） |
|-----|------------|--------|-----------|------------------|
| A100 SXM | NVLink3 | 12 | 300 GB/s | 600 GB/s |
| H100 / H200 / H20 SXM | NVLink4 | 18 | 450 GB/s | 900 GB/s |
| B200 / GB200 | NVLink5 | 18 | 900 GB/s | 1.8 TB/s |

从这两张表可以得到三个结论：

1. **越往外，带宽越低、延迟越高、故障面越大**。L3 引入了光模块、线缆、交换机配置，排障复杂度明显上升。
2. **同一对 GPU 之间可能有多条路径**（比如同时有 PCIe 和 NVLink），实际走哪条由 CUDA/NCCL 的拓扑探测决定。排障第一步永远是确认"实际走了哪条路"。
3. **L1 不一定是 PCIe**。GH200/GB200 这类 Grace 平台上，CPU↔GPU 走的是 NVLink-C2C。

### 0.2.2 软件分层

```
┌─────────────────────────────────────────────────────────────────┐
│ 应用/框架   PyTorch DDP/FSDP · Megatron-LM · DeepSpeed · vLLM/SGLang │
├─────────────────────────────────────────────────────────────────┤
│ 通讯库      NCCL（集合通讯）· NVSHMEM · NIXL/UCX（KV 传输）· MPI    │
├─────────────────────────────────────────────────────────────────┤
│ CUDA        cudaMemcpy/Peer · UVA · CUDA IPC · cuMem 虚拟内存管理   │
├─────────────────────────────────────────────────────────────────┤
│ 驱动/内核   nvidia.ko · nvidia-fabricmanager · nvidia-peermem/dma-buf │
│             ib_core / mlx5_core（OFED/DOCA）                       │
├─────────────────────────────────────────────────────────────────┤
│ 硬件        SM/HBM · PCIe · NVLink/NVSwitch · ConnectX NIC · 交换机 │
└─────────────────────────────────────────────────────────────────┘
```

每一层都可能单独出问题，而且现象往往出现在上层：

- NVLink 硬件完好，但 `nvidia-fabricmanager` 没起来 → NVSwitch 机器上 CUDA 初始化直接失败
- IB 网络完好，但 `nvidia-peermem` 没加载、也没走 dma-buf → NCCL 仍然能跑，只是跨机数据先绕到主机内存再发出去，带宽明显下降（NCCL 日志里能看出 GDR 没启用）

### 0.2.3 控制面与数据面

NCCL 这类通讯库有两条独立的通路，排障时一定要分开看：

| | 控制面（Bootstrap） | 数据面（Data） |
|---|---|---|
| 用途 | rank 互相发现、交换连接信息 | 真正传输张量 |
| 走什么 | TCP socket（`NCCL_SOCKET_IFNAME` 指定网卡） | NVLink / PCIe / IB / RoCE |
| 典型故障 | 多网卡机器选错接口（如 `docker0`）→ **初始化阶段卡住** | 链路降级、GDR 失效 → **能跑但慢**，或运行中 timeout |

"启动就卡住"和"跑一段时间后卡住"往往是完全不同的问题。

## 0.3 单位与口径陷阱

这一节专门讲各种数字为什么"对不上"。看厂商规格、看测试结果、跟同事对数时都要先统一口径。

| 陷阱 | 说明 | 例子 |
|------|------|------|
| **Gb 和 GB** | 网卡用 bit，GPU 互联用 Byte，差 8 倍 | 400 Gb/s NIC = 50 GB/s |
| **单向和双向** | NVLink 宣传值通常是双向之和 | H100 "900 GB/s" 的单向是 450 GB/s |
| **理论值和实测值** | 编码开销、协议头、DMA 效率都会吃掉一部分 | PCIe Gen4 x16 理论 31.5 GB/s，pinned 拷贝实测约 25 GB/s |
| **GB 和 GiB** | nvidia-smi 显存用 MiB，带宽测试一般用 GB（1e9） | 差约 7% |
| **algbw 和 busbw** | 集合通讯的两种带宽口径，见 0.5 节 | 8 卡 AllReduce 两者差 1.75 倍 |

PCIe 各代的单向带宽（x16）：

| 代际 | 单 lane 速率 | 编码 | x16 理论单向 | 典型实测（pinned） |
|------|-------------|------|-------------|------------------|
| Gen3 | 8 GT/s | 128b/130b | 15.75 GB/s | ~12 GB/s |
| Gen4 | 16 GT/s | 128b/130b | 31.5 GB/s | ~25 GB/s |
| Gen5 | 32 GT/s | 128b/130b | 63 GB/s | ~50 GB/s |
| Gen6 | 64 GT/s | PAM4 + FLIT | ~128 GB/s（FLIT 开销后略低） | — |

## 0.4 α-β 模型：延迟和带宽谁说了算

### 0.4.1 模型

一次传输 n 字节的耗时可以近似为：

```
T(n) = α + n / B

α：固定开销（kernel launch、同步、协议握手、链路延迟），与消息大小无关
B：链路有效带宽
有效带宽 = n / T(n)
```

当 `n = α·B` 时，有效带宽恰好是峰值的一半，这个值叫**半带宽消息大小 n½**。

以 α = 10 μs、B = 400 GB/s 为例（接近 H100 NVSwitch 上 NCCL AllReduce 的量级）：

| 消息大小 | 传输时间 n/B | 总耗时 T | 有效带宽 | 谁主导 |
|---------|-------------|---------|---------|-------|
| 64 KB | 0.16 μs | 10.2 μs | 6.3 GB/s | α（延迟） |
| 1 MB | 2.5 μs | 12.5 μs | 80 GB/s | α |
| **4 MB = n½** | 10 μs | 20 μs | **200 GB/s** | 各占一半 |
| 16 MB | 40 μs | 50 μs | 320 GB/s | B（带宽） |
| 256 MB | 640 μs | 650 μs | 394 GB/s | B |

### 0.4.2 对应到真实场景

| 场景 | 典型消息大小 | 所处区间 | 优化方向 |
|------|------------|---------|---------|
| 推理 decode 阶段的 TP AllReduce | 几十 KB ~ 1 MB | 延迟主导 | 减少通讯次数、低延迟算法（LL 协议、one-shot AllReduce）、CUDA Graph |
| 推理 prefill 阶段的 TP AllReduce | 几 MB ~ 几十 MB | 过渡区 | 与计算重叠 |
| 训练 DDP 梯度桶（默认 25 MB） | 25 MB | 带宽主导 | 提升带宽、与反向计算重叠 |
| ZeRO-3/FSDP 参数 AllGather | 几十 ~ 几百 MB | 带宽主导 | 预取、分组 |

这就是为什么**推理和训练对互联的诉求不一样**：训练看带宽，decode 看延迟。只看带宽指标去判断推理集群够不够用，会得出错误结论。

### 0.4.3 从实测数据反推 α 和 B

用 nccl-tests 扫一遍消息大小（`-b 8 -e 8G -f 2`）：

- 最小消息（8 B ~ 1 KB）的 `time` 列 ≈ α
- 最大消息的 `busbw` 列 ≈ B

有了这两个数，就能估算任意消息大小下的耗时，不用每次都去实测。

## 0.5 algbw 和 busbw：集合通讯的带宽口径

nccl-tests 的输出里有两列带宽，很多人只看其中一列，或者拿错列去跟硬件规格比较。

### 0.5.1 定义

```
algbw = S / T                    S：用户视角的数据量，T：耗时
busbw = algbw × F                F：与算法无关的修正系数
```

| 集合操作 | 修正系数 F（n 为 rank 数） | 8 卡时 F |
|---------|--------------------------|---------|
| AllReduce | 2(n-1)/n | 1.75 |
| ReduceScatter | (n-1)/n | 0.875 |
| AllGather | (n-1)/n | 0.875 |
| Broadcast / Reduce | 1 | 1 |
| SendRecv（点对点） | 1 | 1 |

### 0.5.2 为什么需要 busbw

以 Ring AllReduce 为例，n 个 rank 各持有 S 字节，结果每个 rank 都要拿到全部求和。算法分两阶段：

```
阶段 1 ReduceScatter：每个 rank 发送 (n-1) 次，每次 S/n 字节
阶段 2 AllGather    ：每个 rank 发送 (n-1) 次，每次 S/n 字节

每个 rank 实际发送总量 = 2(n-1)/n × S
```

所以每条链路上真实跑的数据量是 S 的 2(n-1)/n 倍。busbw 衡量的就是**链路上真实跑出来的带宽**，可以直接和硬件单向带宽比较，而且不随卡数变化。algbw 则会随卡数增加而下降，不适合跨规模比较。

### 0.5.3 判读示例

```
8×H100 SXM，AllReduce，消息 1 GB，耗时 4.4 ms
algbw = 1 GB / 4.4 ms ≈ 227 GB/s
busbw = 227 × 1.75   ≈ 398 GB/s
对比 NVLink4 单向 450 GB/s → 约 88%，属于健康水平
```

判断标准：**大消息下 busbw 应达到瓶颈链路单向带宽的 80% 以上**。明显偏低就要查链路降级、拓扑异常、环境变量配置。

## 0.6 通讯量估算：先算再测

拿到一个任务，先用公式估一下每步要搬多少数据、大概花多久，再去实测验证。估算和实测差距很大时，往往就是问题所在。

### 0.6.1 常用估算公式

记 P 为参数量，b 为每元素字节数，n 为参与通讯的 rank 数，B 为 busbw。

| 并行方式 | 每步通讯 | 每 rank 发送量 | 耗时估算 |
|---------|---------|--------------|---------|
| DDP | 梯度 AllReduce | 2(n-1)/n × P·b | 发送量 / B |
| ZeRO-3 / FSDP | 前向 AllGather + 反向 AllGather + 梯度 ReduceScatter | ≈ 3(n-1)/n × P·b | 发送量 / B |
| TP（Megatron 式） | 每层前向 2 次 AllReduce，反向 2 次 | 单次消息 = batch × seq × hidden × b | 次数 × T(单次消息) |
| PP | stage 边界 Send/Recv 激活 | 每 micro-batch 一次 batch × seq × hidden × b | 通常不是瓶颈，瓶颈在 bubble |
| EP（MoE） | 每个 MoE 层 dispatch + combine 两次 All2All | 与 top-k、token 数相关 | 详见第 8 章 |

### 0.6.2 示例 1：7B 模型 DDP，单机和双机

假设梯度为 BF16，P·b = 14 GB。如果用 AMP 且主参数是 FP32，DDP 同步的是 FP32 梯度，数据量要翻倍。

| 配置 | n | 每 rank 发送量 | busbw（估） | 每步 AllReduce 耗时 |
|------|---|--------------|-----------|-------------------|
| 单机 8×H100 SXM（NVSwitch） | 8 | 1.75 × 14 = 24.5 GB | ~400 GB/s | **~61 ms** |
| 2 机 16 卡，每卡 1 张 400G NIC（rail-optimized） | 16 | 1.875 × 14 = 26.3 GB | ~350 GB/s | **~75 ms** |
| 2 机 16 卡，每机只有 1 张 200G NIC | 16 | 26.3 GB | ~25 GB/s | **~1.05 s** |

跨机本身并不意味着慢。网卡配足时（每 GPU 一张），busbw 接近单机；网卡不足时，所有 ring 都挤在一张网卡上，busbw 会掉一个数量级以上。"多机比单机还慢"的工单，第一件事就是查 GPU 和 NIC 的配比和亲和关系。

### 0.6.3 示例 2：70B 模型 TP=8 推理 decode

以 Llama-3-70B 为例：hidden = 8192，80 层，TP=8，decode batch = 32，BF16。

```
单次 AllReduce 消息 = 32 × 8192 × 2 B = 512 KB       ← 处于延迟主导区间
每个 decode step 的 AllReduce 次数 = 80 层 × 2 = 160 次

H100 SXM（NVSwitch）：单次约 10~15 μs  → 160 次 ≈ 1.6~2.4 ms
计算侧：每卡权重 140 GB / 8 = 17.5 GB，按 ~3 TB/s 读一遍 ≈ 5.8 ms
→ 通讯约占 decode step 的 20%~30%

纯 PCIe 机型（如 8×L40S）：单次 P2P AllReduce 在几十 μs 量级
→ 160 次可达数 ms，与计算时间相当，TP=8 扩展性很差
```

这解释了两个常见现象：一是 vLLM/SGLang 都实现了自定义的低延迟 AllReduce（依赖 NVLink P2P，条件不满足时回退到 NCCL）；二是 PCIe 机型上往往 TP=4 或 TP=2 加 PP 比 TP=8 更快。以上是量级估算，具体数值要在第 8 章实测。

## 0.7 计算与通讯重叠

真实的 step 时间并不是计算加通讯，而是：

```
step_time ≈ compute_time + exposed_comm_time
exposed_comm_time = 没能被计算掩盖掉的那部分通讯
```

- DDP 在反向传播过程中按桶发起 AllReduce，大部分梯度同步可以和后续层的反向计算重叠
- FSDP 通过预取下一层参数，让 AllGather 和当前层计算重叠
- TP 的 AllReduce 位于计算的关键路径上，很难重叠（这也是 TP 必须走高带宽、低延迟链路的原因）

重叠本身也有代价。NCCL kernel 运行时会占用 SM、L2 和 HBM 带宽，导致同时运行的计算 kernel 变慢（第 1 章 1.6 节）。所以优化目标是降低 exposed 部分，而不是简单地追求"全部重叠"。如何从 Nsight Systems 时间线上量出 exposed 通讯，见第 9 章。

## 0.8 实操：给一台 GPU 机器做通讯基线普查

新机器上线、故障机返修、性能工单排查时，都应该按层把基线测一遍。这里先给出速查表，每条命令的输出怎么解读、异常怎么处理，在对应章节里展开。

| 层 | 检查项 | 命令 | 健康标准 |
|----|-------|------|---------|
| L1 | PCIe 链路速率和宽度 | `nvidia-smi --query-gpu=index,pcie.link.gen.current,pcie.link.gen.max,pcie.link.width.current,pcie.link.width.max --format=csv` | 负载下 current 等于 max。空闲时 GPU 会降速，**需要在有负载时查看** |
| L1 | PCIe 链路（系统侧） | `lspci -vvv -s <BDF> \| grep -E 'LnkCap\|LnkSta'` | LnkSta 速率和宽度与 LnkCap 一致 |
| L1 | H2D / D2H 带宽 | `nvbandwidth -t host_to_device_memcpy_ce device_to_host_memcpy_ce` | 接近 0.3 节的实测参考值 |
| L1/L2 | 拓扑与亲和 | `nvidia-smi topo -m` | GPU 间连接类型符合机型设计，GPU 与 NIC 的亲和符合预期 |
| L2 | NVLink 状态 | `nvidia-smi nvlink -s` | 所有链路 active，速率一致 |
| L2 | NVLink 错误计数 | `nvidia-smi nvlink -e` | CRC/replay 计数不持续增长 |
| L2 | Fabric Manager（NVSwitch 机型） | `systemctl status nvidia-fabricmanager` | active (running)，且版本与驱动一致 |
| L2 | 卡间带宽矩阵 | `nvbandwidth -t device_to_device_memcpy_read_ce` | 各 GPU 对之间数值一致，没有明显偏低的 |
| L3 | IB/RoCE 端口 | `ibstat` / `ibv_devinfo` | State: Active，Physical state: LinkUp，Rate 符合预期 |
| L3 | GPUDirect RDMA 模块 | `lsmod \| grep -E 'nvidia_peermem\|nv_peer_mem'` | 已加载（或确认走 dma-buf 方式） |
| 综合 | 集合通讯 | `./build/all_reduce_perf -b 8 -e 8G -f 2 -g <卡数>` | 大消息 busbw 达到瓶颈链路单向带宽的 80% 以上 |

单机 AllReduce busbw 的经验参考值（大消息、NCCL 默认配置，不同驱动和 NCCL 版本会有差异）：

| 机型 | 瓶颈链路单向带宽 | busbw 参考 |
|------|----------------|-----------|
| 8×A100 SXM（NVSwitch） | 300 GB/s | ~230 GB/s 左右 |
| 8×H100 SXM（NVSwitch） | 450 GB/s | ~360~400 GB/s；开启 NVLS 后可更高 |
| 8 卡纯 PCIe Gen4 | 25 GB/s 左右 | 远低于 NVLink 机型，且受 PCIe Switch 布局影响很大 |

建议把每种机型的普查结果记录成基线。后续出现性能问题时，先和基线对比，能很快判断是硬件问题还是业务问题。

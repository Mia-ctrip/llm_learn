# 第 1 章：卡内通讯（L0）

> 核心问题：一块 GPU 内部，数据是怎么在 SM、各级缓存和 HBM 之间流动的？SM 之间怎么交换数据？通讯 kernel 为什么会拖慢计算？
>
> 前置阅读：[GPU显存层次与Flash_Attention前置知识.md](../GPU显存层次与Flash_Attention前置知识.md)。那篇已经用实验验证了 HBM 带宽上限、Memory-Bound/Compute-Bound、L2 效应和 Tiling。本章不重复这些结论，而是从**通讯视角**补齐片上数据通路的结构、线程间通讯机制和资源争用。

---

## 1.1 为什么把卡内数据搬运当作"通讯"

计算发生在 SM 里，数据住在 HBM 里，两者之间隔着 L2 和片上互联网络。一个 kernel 的执行过程，本质就是"把数据从 HBM 搬到 SM，算完再搬回去"。

从能耗看，片外 DRAM 访问的能耗比一次 FMA 运算高出两到三个数量级。从带宽看，0.1 节已经算过，H100 每从 HBM 读 1 字节需要配约 295 FLOP 才能喂饱 Tensor Core。所以卡内的数据搬运和卡间、跨机通讯是同一类问题，只是尺度不同。

卡内通讯分三类：

| 类型 | 方向 | 内容 | 本章小节 |
|------|------|------|---------|
| **纵向** | 线程 ↔ 存储层级 | 寄存器 ↔ SMEM/L1 ↔ L2 ↔ HBM | 1.3、1.4 |
| **横向** | 线程 ↔ 线程 | warp 内、block 内、cluster 内、跨 SM | 1.5 |
| **争用** | 计算 ↔ 数据搬运 | 通讯 kernel 与计算 kernel 抢 SM/L2/HBM | 1.6、1.7 |

## 1.2 片上拓扑：SM、crossbar、L2、HBM

### 1.2.1 结构图（以 H100 SXM5 为例）

```
GPU 芯片
├── 8 × GPC（Graphics Processing Cluster）
│   └── TPC（每个含 2 个 SM），全卡共 132 个 SM
│       └── SM
│           ├── 4 个处理分区，每个分区有 Warp Scheduler + Tensor Core
│           ├── 寄存器文件 256 KB
│           ├── L1 / Shared Memory 合计 256 KB（SMEM 最多可配 228 KB）
│           └── TMA 单元（Hopper 新增）
├── 片上互联（crossbar / NoC）：所有 SM 都通过它访问 L2
├── L2 Cache 50 MB，分成 2 个 partition
├── 显存控制器 × 10（每个 512-bit）→ 5 个 HBM3 stack，总位宽 5120-bit，80 GB
└── 对外接口：PCIe Gen5 主机接口、18 × NVLink4、Copy Engine
```

### 1.2.2 数据通路图

```
  SM0        SM1        ...        SM131
 ┌──────┐  ┌──────┐              ┌──────┐
 │ Reg  │  │ Reg  │              │ Reg  │      ← 每个 SM 私有
 │L1/SMEM│ │L1/SMEM│             │L1/SMEM│
 └──┬───┘  └──┬───┘              └──┬───┘
    └─────────┴──── 片上 crossbar ───┴─────────┐
                         │                      │
         ┌───────────────┴──────────────┐       │
         │  L2 partition 0 │ L2 partition 1 │  ← 全卡共享，跨 SM 一致性点
         └───────────────┬──────────────┘       │
                         │                      │
              显存控制器 × 10                Hub：PCIe / NVLink / Copy Engine
                         │                      │
                    HBM3 × 5                主机 / 其他 GPU
```

这张图有三个要点：

1. **L2 是全卡唯一的共享缓存**，也是不同 SM 之间数据一致的汇合点。L1 是 SM 私有的，不同 SM 的 L1 之间不保证一致。
2. **SM 访问另一个 partition 的 L2 会多一跳**，延迟更高。硬件自动处理，对编程透明，但在微基准测试里能观察到 L2 延迟出现两档。
3. **PCIe、NVLink、Copy Engine 也挂在这套片上互联上**。其他 GPU 通过 NVLink 写进来的数据，同样要经过本卡的 L2 和 HBM。所以卡间通讯会和本卡计算争用 L2 和 HBM 带宽，这是 1.6 节的硬件基础。

### 1.2.3 常见生产卡的片上参数

| GPU | 架构 | SM 数 | L2 | 每 SM 最大 SMEM | 显存 | 显存带宽 | BF16 稠密算力 | 拐点（FLOP/B） |
|-----|------|------|----|---------------|------|---------|-------------|--------------|
| A100 SXM 80GB | Ampere | 108 | 40 MB | 164 KB | HBM2e 80 GB | 2.04 TB/s | 312 TF | ~153 |
| H100 SXM | Hopper | 132 | 50 MB | 228 KB | HBM3 80 GB | 3.35 TB/s | 989 TF | ~295 |
| H200 SXM | Hopper | 132 | 50 MB | 228 KB | HBM3e 141 GB | 4.8 TB/s | 989 TF | ~206 |
| H20 | Hopper | 以实测为准 | 以实测为准 | 228 KB | HBM3 96 GB | 4.0 TB/s | 148 TF | **~37** |
| B200 | Blackwell | 以实测为准 | 以实测为准 | 以实测为准 | HBM3e 180~192 GB | 8 TB/s | ~2,250 TF | ~281 |
| L40S | Ada | 142 | 96 MB | 100 KB | GDDR6 48 GB | 864 GB/s | 362 TF | ~419 |

> 规格来自公开资料，标"以实测为准"的项用 1.8.1 节的方法在真机上查询后补齐。

拐点 = 算力 / 显存带宽，表示一个 kernel 的算术强度至少要达到多少，才能从 Memory-Bound 进入 Compute-Bound。H20 的拐点只有 37，意味着它在几乎所有负载下都更接近 Compute-Bound；而 L40S 的拐点高达 419，大部分 LLM 推理负载在它上面都是 Memory-Bound。1.9.1 节会用这个结论分析 decode 性能。

## 1.3 纵向通讯：存储层级

### 1.3.1 各层级对比（H100）

| 层级 | 容量 | 作用域 | 管理方式 | 延迟量级 | 带宽量级 |
|------|------|-------|---------|---------|---------|
| 寄存器 | 256 KB/SM，单线程最多 255 个 | 线程私有 | 编译器分配 | ~1 cycle | 最高 |
| Shared Memory | 最多 228 KB/SM | block 内；Hopper 起可在 cluster 内跨 SM | 程序员显式管理 | ~30 cycle | 全卡合计数十 TB/s |
| L1 | 与 SMEM 共用 256 KB | SM 私有 | 硬件 | ~30~40 cycle | 同上 |
| L2 | 50 MB | 全卡共享 | 硬件，可设置驻留策略 | ~200~300 cycle | ~10 TB/s 量级 |
| HBM | 80 GB | 全卡，也可被其他 GPU 通过 P2P 访问 | 硬件 | ~500+ cycle | 3.35 TB/s |

> 延迟是公开微基准测试给出的量级，不同测量方法差异较大，理解相对关系即可。

### 1.3.2 合并访存：把小包攒成大包

GPU 访问全局内存的最小粒度是 **32 字节的 sector**，一条 cache line 是 128 字节（4 个 sector）。

```
理想情况：一个 warp 的 32 个线程读连续的 32 个 float（4 B）
         → 正好 128 B = 4 个 sector，带宽利用率 100%

步长为 2：32 个线程读 a[0], a[2], a[4] ... a[62]
         → 覆盖 256 B = 8 个 sector，但只用到一半数据，利用率 50%

完全随机：最坏情况每个线程单独占 1 个 sector
         → 32 个 sector 里只有 4 B × 32 有用，利用率 12.5%
```

这和 0.4 节的 α-β 模型是同一个道理：每次事务都有固定开销，访问越零散，有效带宽越低。NCCL 把小消息攒成大块再发，DDP 把梯度分桶后再做 AllReduce，原理相同。

ncu 中判断合并访存效果的指标：

```
l1tex__t_sectors_pipe_lsu_mem_global_op_ld.sum      # 实际读取的 sector 数
l1tex__t_requests_pipe_lsu_mem_global_op_ld.sum     # 读请求数
# 两者相除 = 每次请求平均读多少个 sector
# 4 字节连续访问的理想值是 4，明显偏大说明访存不连续
```

### 1.3.3 Shared Memory 的 bank conflict

SMEM 被分成 **32 个 bank**，每个 bank 宽 4 字节。一个 warp 内的多个线程访问**同一个 bank 的不同地址**时，访问会被串行化。

```
无冲突：线程 i 访问 smem[i]            → 32 个线程落在 32 个 bank，一次完成
2 路冲突：线程 i 访问 smem[i * 2]      → 每个 bank 被 2 个线程访问，耗时翻倍
广播：所有线程访问同一地址            → 硬件广播，不算冲突
```

典型场景是矩阵转置时按列读 SMEM。常见解决办法是给每行多分配一个元素做 padding（`__shared__ float tile[32][33]`），把同一列的元素错开到不同 bank。

ncu 指标：`l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_ld.sum`（读冲突次数）。

### 1.3.4 L2：一致性点和驻留控制

L2 有两个关键特性：

1. **全卡一致性点**：一个 SM 写入的数据，其他 SM 要可靠地读到，必须经过 L2，并配合内存栅栏（1.5.4 节）。
2. **驻留控制**（Ampere 起）：可以把一部分 L2 预留给热点数据，减少它们被其他访问挤出去的概率。

```cpp
// 先预留一部分 L2 作为 persisting 区域
cudaDeviceSetLimit(cudaLimitPersistingL2CacheSize, 20 * 1024 * 1024);

// 再给某个 stream 设置访问策略窗口
cudaStreamAttrValue attr = {};
attr.accessPolicyWindow.base_ptr  = hot_ptr;           // 热点数据起始地址
attr.accessPolicyWindow.num_bytes = hot_bytes;
attr.accessPolicyWindow.hitRatio  = 1.0f;              // 窗口内多大比例按 persisting 处理
attr.accessPolicyWindow.hitProp   = cudaAccessPropertyPersisting;
attr.accessPolicyWindow.missProp  = cudaAccessPropertyStreaming;
cudaStreamSetAttribute(stream, cudaStreamAttributeAccessPolicyWindow, &attr);
```

适用场景是反复读取、但总量明显小于 L2 的数据。L2 的切分还会受 MIG 影响，见 1.7 节。

## 1.4 异步数据搬运单元

前面讲的都是"线程自己去读写内存"。从 Ampere 开始，GPU 加入了越来越多的专用搬运硬件，让数据搬运和计算可以并行。

| 机制 | 架构 | 路径 | 谁发起 | 特点 |
|------|------|------|-------|------|
| 普通 load/store | 全部 | HBM → L2 → L1 → 寄存器 → SMEM | 每个线程 | 数据要经过寄存器，搬运期间线程只能等 |
| `cp.async` | Ampere 起 | HBM → L2 → SMEM，不经过寄存器 | 每个线程 | 异步发起，可做多级流水（double buffering） |
| **TMA** | Hopper 起 | HBM ↔ SMEM 整块 tile，支持 cluster 内 multicast | 单个线程发起，硬件生成地址 | 搬运线程极少，其他 warp 专心计算 |
| Copy Engine | 全部 | H2D / D2H / P2P 的 DMA | 驱动，通过 stream 下发 | 完全不占 SM，第 2 章详述 |

### 1.4.1 TMA 与 warp specialization

TMA（Tensor Memory Accelerator）拿到一个张量描述符后，可以自动按 tile 搬运多维数据，地址计算和边界处理都由硬件完成。这让 kernel 可以按角色分工：

```
Producer warp（1 个线程发 TMA 指令） ──► 把下一块 tile 搬进 SMEM
Consumer warpgroup（WGMMA 指令）     ──► 用当前 tile 做矩阵乘
两者通过 SMEM 中的 mbarrier 同步，形成流水线
```

FlashAttention-3 和 CUTLASS 3.x 的 Hopper kernel 都采用这种结构。FlashAttention-2 没有使用 TMA 和 WGMMA，所以在 H100 上达不到峰值，FA3 论文报告 FP16 下比 FA2 快 1.5~2 倍。这也说明：**同样是 H100，用不用新的数据搬运硬件，性能差距很大**。排查"H100 比预期慢"时，要确认用到的 kernel 是否针对 Hopper 做了适配。

### 1.4.2 Copy Engine

Copy Engine（CE）是独立的 DMA 引擎，专门负责 `cudaMemcpyAsync` 这类拷贝，不占用 SM。`deviceQuery` 里的 `Concurrent copy and kernel execution: Yes with N copy engine(s)` 就是它的数量。

值得注意的是，**NCCL 在节点内默认用 SM 上运行的 kernel 来搬数据**，而不是用 CE，因为它需要在搬运的同时做 reduce 运算。这意味着通讯会占用计算资源，见 1.6 节。

一、抽象分层模型（卡型无关）

Layer 6: 应用/框架层    (PyTorch/TensorFlow/DeepSpeed/NCCL)
Layer 5: CUDA Runtime层  (cudaGetDeviceCount, cudaMalloc...)
Layer 4: CUDA Driver层   (建立Context，真正触达计算引擎)
Layer 3: NVML/管理面层   (nvidia-smi，只读查询/轻量ioctl)
Layer 2: GPU固件层       (VBIOS/Inforom，Ampere+还有GSP固件)
Layer 1: 内核驱动层      (nvidia.ko / nvidia_uvm.ko / nvidia_drm.ko)
Layer 0: 物理/链路层     (PCIe链路、供电、散热、NVLink)

判断故障所在层的关键手段：用"能走到哪一层"倒推故障点，而不是死记某个错误码对应哪张卡。

各层快速自检：常用命令 + 最常见报错（排障时按 Layer 0→6 从下往上验证，哪一层第一次卡住，故障边界就在它和上一层之间）

Layer 0 物理/链路层
  检测：lspci | grep -i nvidia；nvidia-smi -q -d PCIE；nvidia-smi nvlink -s
  常见报错：lspci查不到卡；dmesg出现"GPU has fallen off the bus"；PCIe链路宽度从x16降到x1/x4；温度/功耗触发降频

Layer 1 内核驱动层
  检测：lsmod | grep nvidia；ls -l /dev/nvidia*；nvidia-smi（这层出问题，这条命令直接失败）
  常见报错："NVIDIA-SMI has failed because it couldn't communicate with the NVIDIA driver"；/dev/nvidia* 缺失；dmesg里"NVRM: API mismatch"（驱动版本与内核模块不一致，常见于升级后未重启）

Layer 2 GPU固件层
  检测：nvidia-smi -q | grep -iE "vbios|inforom"；dmesg -T | grep -iE "gsp|xid"
  常见报错："Inforom corruption detected"；Xid 119/120（GSP固件握手/RPC超时）；nvidia-smi正常但CUDA初始化报Error 802/999（见本目录案例记录，卡在这层与Layer 4之间）

Layer 3 NVML/管理面层
  检测：nvidia-smi；nvidia-smi -q
  常见报错：这一层通常是"对照组"——能跑通说明Layer 0/1/2都正常；少见异常是命令卡住不返回（说明卡可能已掉卡或驱动死锁，而非这层本身的问题）

Layer 4 CUDA Driver层
  检测：deviceQuery（CUDA samples自带，最通用）；最小复现程序调用cudaGetDeviceCount；nvidia-smi -q -d ROW_REMAPPER；nvidia-smi -r（判断能否软件reset）
  常见报错：CUDA Error 802: system not yet initialized；CUDA Error 999: unknown error；有pending row remap时报ECC相关的context创建失败

Layer 5 CUDA Runtime层
  检测：dmesg -T | grep -i xid（运行中途挂掉首选）；compute-sanitizer跑kernel；nvidia-smi dmon -s u
  常见报错：illegal memory access was encountered（对应Xid 31，多为软件bug）；illegal instruction（Xid 13）；Xid 48/63/64（ECC/页错误，偏硬件）

Layer 6 应用/框架层
  检测：python -c "import torch;print(torch.cuda.is_available())"；NCCL_DEBUG=INFO跑程序；nccl-tests的all_reduce_perf
  常见报错：ProcessGroupNCCL is only supported with GPUs, no GPUs found!（见本目录案例记录，根因在下层，这层只是出口）；NCCL timeout / Watchdog caught collective operation timeout

二、专题：两大核心排障工具——nvidia-smi 与 dmesg

日常GPU运维大多止步于跑一下nvidia-smi看着"正常"就完事，但这两条命令各自能验证的范围都有明确边界，而且是互补关系：nvidia-smi是**实时快照**，dmesg是**时序事件流**。两者缺一都排不出完整的故障链条。

2.1 nvidia-smi：到底在测什么

本质：nvidia-smi是NVML（管理库）的命令行客户端，走"管理面"ioctl通路，只读查询硬件/固件状态，不建立CUDA Context，不需要和固件做完整握手。

前置依赖——"命令存在"和"命令能跑通"是两件不同的事：
- 命令是否存在：依赖驱动包的用户态部分（nvidia-smi二进制、NVML库）已安装。没装过驱动 → command not found，这跟硬件在不在无关，纯粹是"装没装软件"。
- 命令执行后能否正常输出GPU信息表：依赖内核态模块(nvidia.ko)已成功加载、设备节点可访问——这才是真正验证Layer 1健康。两者会脱节的典型场景：内核升级后模块没重新编译/加载，或Secure Boot拦截了未签名模块——此时命令文件还在、能被调用，但一执行就报"couldn't communicate with the NVIDIA driver"。

它到底能验证到哪一层：
- Layer 0（物理/链路）：能，`nvidia-smi -q -d PCIE`、`nvidia-smi nvlink -s` 直接读链路状态
- Layer 1（内核驱动）：能，命令能否正常通信本身就是这一层的健康信号
- Layer 2（GPU固件）：只能验证"浅层只读查询能通过"，不能验证"支撑CUDA Context创建所需的深层状态机是否完全就位"——这是最容易被误解、也是案例记录里那个A100问题的根源
- Layer 3（NVML/管理面）：nvidia-smi本身就是这一层，不是它检测的对象
- Layer 4及以上（CUDA Driver/Runtime/应用框架）：测不到，必须实际走一次对应路径（`deviceQuery`、最小CUDA程序调用`cudaGetDeviceCount`、`torch.cuda.is_available()`）才能确认

深层代理信号（只能提示风险，不是确定性结论）：
- `nvidia-smi -q -d ROW_REMAPPER` → Pending状态位，提示还有remap没生效，需要一次GPU reset
- `nvidia-smi -q`中的"GPU Reset Status"（较新驱动才有）→ Reset Required: Yes/No
- `nvidia-smi -q -d ECC` → Uncorrectable错误计数异常高是风险信号
- Clocks Event Reasons → 异常降频提示硬件状态不正常
这些都只是proxy signal，唯一权威的测试仍然是真正触发一次Layer 4路径——这正是案例记录里排查到最后还要专门写一个`simple_cuda_test.cu`去跑的原因。

一句话总结：nvidia-smi能回答"链路通不通、驱动模块活不活、固件表层数据读不读得出来"，回答不了"固件深层状态机是否真的就位、CUDA能不能真正跑起来"。

2.2 dmesg：原理与判断准则

本质：dmesg读取的是内核的环形日志缓冲区（ring buffer），里面是内核代码和内核模块（包括nvidia.ko）通过printk()主动写入的一条条消息。它是**事件/消息日志**，不是"指令执行记录"或"指令trace"——没有任何代码会去记录"每一条指令怎么执行"，driver只会在自己判断"这件事值得记一笔"时才调用printk写进去。

和nvidia-smi的本质区别：
- nvidia-smi是**实时快照**：只能看到"现在"这一刻的状态值
- dmesg是**时序事件流**：能看到"什么时候发生了什么"，瞬时性的硬件异常（一次illegal memory access、一次掉卡）如果没有连续轮询nvidia-smi根本抓不住那个瞬间，但dmesg里带时间戳的记录会一直留着，直到被覆盖或重启清空
- 代价：dmesg只是**环形缓冲区**，容量有限，日志量大时老记录会被滚掉；系统重启后缓冲区清空，之前的记录会丢失（这时要退而用`journalctl -k -b -1`查上一次开机的内核日志，或看是否持久化到了`/var/log/kern.log`）

谁会写进dmesg、谁不会——这是用好这条命令最关键的判断依据：
- **会写入**：GPU硬件通过中断上报给内核的事件（ECC错误、非法内存访问被MMU/硬件捕获、GSP固件RPC超时等），nvidia.ko接到中断后选择把它翻译成一条Xid消息记下来。覆盖范围：Layer 0（PCIe AER）、Layer 1（模块自身的加载/卸载/版本不匹配事件）、Layer 2（固件上报的Xid，如119/120）、部分Layer 4/5（硬件探测到异常并触发中断，比如Xid 31/48）
- **不会写入**：纯软件/API层面、全程在用户态处理掉、从未触发硬件中断的错误。比如`CUDA out of memory`（纯显存记账失败）、CUDA API误用类错误（invalid value/invalid device）、NCCL通信超时、Python异常、"ProcessGroupNCCL is only supported with GPUs, no GPUs found!"这类Layer 6应用层报错——这些dmesg里完全查不到

常用命令：
```
dmesg -T                              # 加人类可读时间戳，排障必备（不加-T只有开机后秒数，没法对时）
dmesg -T | grep -i nvidia              # 所有nvidia相关内核日志
dmesg -T | grep -i xid                 # 专门抓Xid事件，排障的第一条命令
dmesg --level=err,crit,alert,emerg     # 按严重级别过滤
journalctl -k -b -1                    # systemd系统上查"上一次开机"的内核日志（重启后dmesg已清空时用）
```

跨卡型通用的核心工具：Xid 错误码体系——Xid是NVIDIA从Tesla到Quadro到GeForce/RTX统一的硬件事件编码系统，不随卡型变化含义（只是某些Xid只在特定代际/特定SKU上会触发），所以`dmesg -T | grep -i xid`不管什么卡永远是第一步。高频编号（覆盖大部分场景）：
- Xid 13/31：非法指令/非法内存地址访问，多数是应用层kernel越界，软件bug
- Xid 48：Double Bit ECC错误（DBE），硬件内存错误，持续出现要考虑RMA
- Xid 63/64：Row Remapper pending/failure，需要reset才能生效
- Xid 79：GPU掉下总线（fallen off the bus），典型硬件/链路问题
- Xid 119/120：GSP固件RPC超时，固件握手类问题

判断准则（避免常见误判）：
1. **"有Xid"≠"硬件一定坏了"，只代表硬件层探测到了异常**。例如Xid 31很多时候根因是应用自己写的CUDA kernel越界访问——是软件bug让硬件的MMU去报了异常，不能直接倒推"硬件故障"，还要结合具体编号判断。
2. **"没有Xid"也不能100%排除Layer 0~2的问题**。像"固件没完全就位"这类问题本质是状态机某环节没走完，不一定表现为一次会触发中断的离散硬件事件，往往只有CUDA Driver真的去建立Context、撞上这个没完成的状态时，才会被动暴露出软件层返回码（如Error 802），这个过程未必产生对应的Xid。所以观察到dmesg干净，只能说"没看到持续性/明显的硬件中断类故障"，不是确诊依据。
3. **观察位置和窗口要对**：容器内查dmesg经常因为`kernel.dmesg_restrict`或namespace隔离直接看不到任何东西，这是假阴性，必须去host上确认；观察窗口要覆盖故障复现的时刻，且系统不能在期间重启过，否则记录可能已经丢失。
4. **结论要交叉验证，不要单独靠dmesg下定论**：有无Xid应该和`nvidia-smi -q -d ROW_REMAPPER`、`nvidia-smi -r`等其它证据放在一起看，三者互相印证才能把"推断"升级成"结论"（见本目录案例记录中Error 802的排查思路）。

三、通用诊断铁律：NVML能过 ≠ CUDA能过

这一条在所有卡型上都成立，原理是通用的，也正是上一节结论的另一种表述——
- NVML走的是管理面通路（读寄存器/固件状态），不需要建立计算上下文，不触碰显存ECC映射、不需要和固件做完整握手。
- CUDA Driver初始化需要GPU的硬件状态机完全就位：显存管理单元、ECC/ReMap表、(Ampere+)GSP固件握手全部OK。

所以"nvidia-smi正常、CUDA初始化失败"这个现象模式本身就是一个强信号：问题卡在 Layer 2↔Layer 4 之间，而不是驱动安装或挂载问题（Layer 1/容器层已经排除）。这条规律对 V100、A100、H100、L40、甚至消费级RTX都适用，只是具体字段名字不同。

用法：拿到一个新报错，先问"这是哪一类现象"，再决定往哪个方向排查，而不是先查这个报错码对应哪款GPU的哪个已知bug。

五、通用SOP（不针对卡型，适用任意型号）

1. 复现范围定界：裸机直接跑 vs 容器内跑，判断是容器隔离问题还是硬件/驱动问题（这一步排除了"假性GPU故障"，很多报错其实是容器devcie映射或cgroup问题伪装成硬件故障）
2. 看Xid：dmesg -T | grep -i xid，这是通用故障分类的起点
3. 看硬件状态字段是否异常（不是看"有没有"，是看"状态值"）：
nvidia-smi -q
3. 重点字段跨卡型通用：ECC Errors、Pending状态位（部分卡叫Row Remapper，老卡叫Retired Pages）、Clock/Pstate是否卡在异常档位、PCIe link width/speed是否降级
4. 判断是否可软件恢复：尝试 nvidia-smi -r（GPU reset）。能reset成功 → 软件级可恢复问题；reset失败/报busy → 需要物理repower或整机重启
6. 归因到层：按上面的分层模型，把"reset能不能修"、"repower能不能修"、"仍然必须RMA"作为最终分水岭

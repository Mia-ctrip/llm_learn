三、现象描述

- `nvidia-smi` 可以正常执行，输出正常
- 内核模块 `nvidia`、`nvidia_uvm` 加载正常
- 容器内 `/dev/nvidia*` 设备全部挂载成功
- 但任何CUDA程序调用 `cudaGetDeviceCount` 均返回 **Error 802: system not yet initialized**
- 上层表现为 PyTorch/DeepSpeed 初始化NCCL进程组时报错 "no GPUs found"（本质是CUDA Runtime拿不到可用设备数）

四、已验证的测试结果

- 自行编写最小复现程序 `simple_cuda_test.cu`，仅调用 `cudaGetDeviceCount`
- 编译：`nvcc simple_cuda_test.cu -o simple_cuda_test`
- 运行：`./simple_cuda_test`
- 结果：输出 **error 802**，与业务报错现象一致，确认问题与DeepSpeed/训练框架无关，是CUDA Runtime层本身无法初始化

五、初步判断

GPU硬件上下文损坏：NVML仍可读取（nvidia-smi正常），但CUDA Runtime无法初始化（Error 802）。现象符合"设备可见、NVML正常、CUDA初始化失败"这一类，指向 Layer 2（GPU固件层）与 Layer 4（CUDA Driver层）之间的边界问题，而非驱动安装、设备挂载或容器配置问题。

六、根因确认：nvidia-fabric-manager 未安装/未启动

最终定位：该A100为NVSwitch全互联机型（8卡SXM），GPU间通信依赖NVSwitch交换芯片，而NVSwitch的拓扑发现、路由配置必须由`nvidia-fabric-manager`这个用户态守护进程在开机后完成。本机驱动装了核心的`nvidia-driver`，但没有配套安装/启动`nvidia-fabric-manager`，导致fabric一直没有被标记为ready。

为什么现象恰好是"nvidia-smi正常、cudaGetDeviceCount报802"：
- `nvidia-smi`/NVML查询的是单张GPU芯片自己的寄存器状态（温度、显存、时钟），跟NVSwitch有没有配置完成无关，所以能正常返回——这解释了第五部分"初步判断"里"NVML能过"这一半现象
- CUDA Driver在建立Context前，NVSwitch机型上多了一道前提检查："整个fabric是否已配置完成"。fabric manager没跑起来，这道检查永远过不去，CUDA初始化卡在这里返回Error 802（"system not yet initialized"中的system特指整个fabric系统，不是单张GPU）——解释了"CUDA过不去"这一半现象

验证与修复命令：
```
systemctl status nvidia-fabricmanager          # 服务是否安装、是否在跑
nvidia-smi -q | grep -A5 "Fabric"              # 较新驱动nvidia-smi -q会暴露Fabric State字段，"Completed"才正常
cat /var/log/fabricmanager.log                 # 拓扑发现/配置失败的详细日志
systemctl enable --now nvidia-fabricmanager    # 安装对应驱动版本的fabric-manager包后启动服务
```
修复后重新执行`simple_cuda_test.cu`，`cudaGetDeviceCount`直接返回成功，未重启整机。

- [x] dmesg -T | grep -i xid 的输出 —— 本例中无相关Xid，因为fabric未就位是一个前提检查未通过，不是硬件中断事件，不会产生Xid记录（印证了"没有Xid不能排除Layer 0~2类问题"这条判断准则）

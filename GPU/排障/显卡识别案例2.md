一、原始报错

```
2026-09-22 20:40:07 - Pod|r100056905-91074811-zmww2 - FailedMount, MountVolume.MountDevice failed for volume "pv-juicefs-pro-infer-ai-model-artifacts" : kubernetes.io/csi: attacher.MountDevice failed to create newCsiDriverClient: driver name csi.juicefs.com not found in the list of registered CSI drivers

2026-09-22 20:40:19 - Pod|r100056905-91074811-zmww2 - Failed, Error: failed to start container "app": Error response from daemon: failed to create shim task: OCI runtime create failed: runc create failed: unable to start container process: error during container init: error running hook #0: error running hook: exit status 1, stdout: , stderr: nvidia-container-cli: device error: GPU-a1e905ce-b521-df47-b30d-c8476a89f93b: unknown device: unknown
```

二、现象分类：这是两条独立但相关的报错，且性质和案例1截然不同

- 第一条：JuiceFS CSI 挂载失败，`driver name csi.juicefs.com not found in the list of registered CSI drivers`——纯存储层问题，与GPU无关，本质是CSI Node插件在这个节点上没有正常注册
- 第二条：`nvidia-container-cli: device error: ... unknown device: unknown`——GPU相关，但发生在**OCI runtime hook阶段**，也就是容器进程还没启动、业务代码/CUDA Runtime根本没有机会被调用——比案例1里的Error 802还要靠前一层
- 两条报错同时出现在同一个Pod的调度过程里，共同模式是"某个节点级守护组件（CSI node插件 / nvidia-device-plugin）还没把自己的状态同步给kubelet，但Pod已经被调度上来了"，指向节点级的编排层问题，而非单一GPU硬件故障

三、报错原理：nvidia-container-cli 如何校验GPU

容器启动时，`nvidia-container-cli`拿到k8s/`NVIDIA_VISIBLE_DEVICES`传入的GPU UUID，向NVML查询"这个UUID对应的卡是否存在"。NVML说"不认识这个UUID"，就报`unknown device`。

这意味着：**调度器/设备插件认为这个节点上有这块UUID为`GPU-a1e905ce-...`的卡，但NVML实际枚举到的卡列表里没有它**——是"编排层对硬件现状的认知"和"硬件实际现状"不一致，不是显卡硬件本身损坏的证据。

四、根因定位：k8s侧缓存的GPU UUID 与宿主机实际UUID 不一致

具体成因（云虚机场景特有）：宿主机显卡损坏，云厂商在物理机层面做了更换（换卡/换宿主机），但对外保证虚机身份不变。虚机内实际看到的GPU UUID因此发生了变化，但k8s这一侧缓存的还是旧UUID，于是出现"Pod按旧UUID去挂载，host上查无此UUID"的错配。

这个场景区别于传统物理机：物理机直通场景下，卡坏了通常虚机/宿主机也随之挂掉，不会出现"虚机还活着但卡被偷偷换了"的情况；云环境里虚机身份与物理硬件解耦，才会出现这种"无感换卡"导致的UUID错配，是云环境特有的一类新根因。

五、关键机制：kubelet 的本地缓存与集群全局视图的边界

kubelet是**每个node各自独立一份**的进程（worker node及可调度的master node上都有），不是master集中管理。要理解这次故障为什么只能登录到具体node才能发现，需要分清"哪些信息留在kubelet本地"、"哪些信息才会上报到控制面"：

kubelet本地维护的信息：
- device-plugin的checkpoint文件：`/var/lib/kubelet/device-plugins/kubelet_internal_checkpoint`
- 这个文件记录的是**具体到UUID级别**的信息：这台机器有哪些GPU（每张卡的UUID）、每张卡当前分配给了哪个Pod/container
- 这份数据只在**机器扩容/device-plugin注册时写入一次**，之后不会主动轮询、也不会被动触发更新，只存在于这台node本地，从不同步到etcd或apiserver

上报到控制面（apiserver → etcd）的信息：
- kubelet只把设备情况**汇总成数量**写进Node对象：
  ```yaml
  status:
    allocatable:
      nvidia.com/gpu: "8"     # 只有数量，没有具体UUID
  ```
- 调度器做调度决策时只看这个数量够不够，具体"分配哪张物理卡给哪个Pod"的决策是kubelet本地的device manager自己做的，调度器完全不掌握UUID信息

两层视图的边界：
```
┌─────────────────────────────────────────────────────────┐
│  etcd / apiserver（集群全局视图）                         │
│  只知道："这个node有8张卡"（数量）                         │
└─────────────────────────────────────────────────────────┘
                         ▲ 只上报数量，不上报UUID
                         │
┌─────────────────────────────────────────────────────────┐
│  kubelet（node本地，这次案例卡住的地方）                   │
│  本地checkpoint文件记录：UUID-A → Pod X 已分配             │
│  这份记录只在扩容/device-plugin注册时写一次，之后不刷新     │
└─────────────────────────────────────────────────────────┘
                         ▲ UUID信息不会主动同步，只有kubelet重启时
                         │ 重新走一遍device-plugin注册流程才会刷新
┌─────────────────────────────────────────────────────────┐
│  宿主机实际硬件（云厂商换卡后，UUID已经变了）                │
└─────────────────────────────────────────────────────────┘
```

所以：数量没变（还是8张卡）时，apiserver/etcd里的`allocatable`字段完全看不出异常，控制面层面"一切正常"；具体UUID变了，这个信息只存在kubelet本地文件里，而且是一次性写入、不会被动或主动刷新的，只有触发kubelet重新走一遍device-plugin注册流程（即重启kubelet），才能让它重新获取当前host真实的UUID列表。这解释了为什么单纯"重建pod"或"换机器"是治标，而**重启kubelet才是对症的**。

六、验证与解决方案

确诊前提——先确认UUID是真的"不存在"还是"缓存没刷新"：
```bash
nvidia-smi -L   # 在出问题的host上跑，看能否查到GPU-a1e905ce-...这个UUID
```
- host上能查到这个UUID → 纯编排层缓存滞后，不涉及硬件风险
- host上查不到这个UUID → 需要进一步确认host侧GPU是否真的发生了变化（如本案例的云厂商物理机级换卡）

方案对比：

| 方案 | 效果 | 说明 |
|---|---|---|
| 重新创建pod（原地重调度） | 治标，有时自愈 | 若节点刚启动、device-plugin还在注册窗口期内，等一会可能自愈；若缓存已固化则无效 |
| 换一台机器 | 止血，不解决根因 | 保证业务先跑起来，但问题节点的缓存错配依然存在，下次调度上去还会复现 |
| **重启该node上的kubelet** | **真正修复** | 强制kubelet重新走device-plugin的注册/ListAndWatch流程，刷新本地checkpoint文件为当前host真实的UUID列表 |

延伸改进方向：如果云厂商静默换卡的情况会反复出现，可以考虑加一个定期健康检查（如cronjob），定期对比`nvidia-smi -L`的实际UUID和kubelet本地缓存里的UUID，提前发现不一致并主动触发kubelet重启，把"业务容器起不来"这种用户可见的故障，提前变成后台自愈、业务无感。

七、与案例1的本质区别

- 案例1（显卡识别案例记录.md）：单机CUDA Runtime对GPU固件/NVSwitch fabric状态的前提检查未通过（Layer 2↔4边界），容器已经起来，是业务进程内部报错（Error 802），根因在nvidia-fabric-manager未启动，解决手段是启动服务，不涉及k8s
- 案例2（本文档）：k8s编排层（kubelet本地缓存）与宿主机实际硬件状态不一致，发生在容器启动前的OCI hook阶段，报错压根没走到CUDA那一层，根因在编排层而非硬件本身，不需要reset、不需要RMA，解决手段是刷新kubelet侧的设备缓存

一句话总结：这类"unknown device"报错的第一反应不该是怀疑显卡硬件坏了，而是先确认k8s侧缓存的UUID和host实际UUID是否对齐——对不齐，刷新缓存（重启kubelet）；对齐但host上确实没有这块卡，才需要转向host侧硬件排查。
